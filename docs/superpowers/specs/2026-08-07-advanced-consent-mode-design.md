# Google 고급 동의 모드 최소수집 설계

**작성일:** 2026-08-07
**상태:** 구현 전 검토 대기

## 배경

현재 HanBuddy는 사용자가 분석 쿠키에 동의한 뒤에만 Google Analytics와 Meta Pixel을 불러온다. 이 방식은 개인정보 보호에는 보수적이지만, 동의하지 않은 방문의 유입 캠페인까지 전부 보이지 않아 UTM 기반 유입 성과를 파악하기 어렵다.

한편 최근 추가된 `/apply/`는 이름, 연락처 등 개인정보를 입력받아 Google Sheets와 Discord로 전달한다. 마케팅 페이지의 UTM 측정과 신청자의 개인정보가 자동으로 결합되지 않도록 분석 영역과 신청 영역을 명확히 분리해야 한다.

이 설계는 Google 고급 동의 모드를 제한적으로 적용해 마케팅 페이지의 최소한의 UTM 유입량을 집계하되, 신청 데이터나 행동 이벤트와 연결하지 않는 것을 목표로 한다. 이는 위험을 줄이기 위한 기술 설계이며 법률 자문이나 규제 준수 보증을 대신하지 않는다.

참고 문서:

- [Google 동의 모드 설정](https://developers.google.com/tag-platform/security/guides/consent?consentmode=advanced&hl=ko)
- [Google 태그 개인정보 보호 설정](https://developers.google.com/tag-platform/security/guides/privacy)

## 목표

- 분석 쿠키를 거부하거나 아직 선택하지 않은 방문도 마케팅 페이지에서 UTM 캠페인별 방문량을 제한적으로 집계한다.
- 비동의 상태에서는 쿠키와 브라우저 저장소를 사용하지 않고, 허용된 UTM 값 이외의 쿼리나 세부 리퍼러를 Google에 보내지 않는다.
- CTA 클릭, 스크롤, 섹션 노출, 신청 퍼널 같은 행동 이벤트와 Meta Pixel은 명시적 동의 뒤에만 활성화한다.
- `/apply/`에서는 동의 전 Google 태그를 불러오지 않으며, UTM·리퍼러와 신청 개인정보의 자동 결합을 차단한다.
- 기존의 빌드 없는 정적 사이트 구조와 의존성 없는 Vercel Function을 유지한다.

## 비목표

- 비동의 사용자를 재식별하거나 세션 단위로 추적하지 않는다.
- UTM을 쿠키, `localStorage`, `sessionStorage`, 서버, Google Sheets 또는 Discord에 보존하지 않는다.
- 광고 개인화, 리마케팅, 교차 기기 추적을 비동의 상태에서 활성화하지 않는다.
- 신청 완료와 특정 UTM 캠페인을 사용자 단위로 연결하지 않는다.
- 새 분석 도구, CMP, 패키지 관리자 또는 빌드 시스템을 도입하지 않는다.

## 페이지별 분석 정책

| 페이지 | 동의 전/거부 | 동의 후 |
|---|---|---|
| `/`, `/about/`, `/events/*`, `/privacy/` | 운영 도메인에서 Google 태그를 모든 저장 동의가 거부된 상태로 불러오고, 정제된 페이지뷰 1회만 전송 | Google Analytics 행동 이벤트와 Meta Pixel 활성화 |
| `/apply/` | Google·Meta 외부 태그를 불러오지 않고 페이지뷰와 행동 이벤트를 전송하지 않음 | Google Analytics 신청 퍼널 이벤트와 Meta Pixel 활성화 |
| 로컬·미리보기·비운영 호스트 | 전송 없음 | 전송 없음 |

마케팅 페이지에는 Google 고급 동의 모드를 적용하고, 개인정보 입력 페이지인 `/apply/`에는 기존의 기본 동의 모드 수준을 유지하는 혼합 구조다. 운영 호스트 판정은 현재 코드의 production-host 가드를 재사용한다.

## 데이터 흐름

### 마케팅 페이지의 비동의 방문

1. 페이지 스크립트가 Google의 네 가지 동의 신호를 기본 `denied`로 설정한다.
2. `ads_data_redaction`을 활성화하고 Google Signals와 광고 개인화 신호를 비활성화한다.
3. 자동 페이지뷰를 `send_page_view: false`로 막는다.
4. 현재 URL을 로컬에서 정제해 출처, 경로, 허용된 UTM만 포함한 `page_location`을 만든다.
5. 세부 경로나 쿼리가 없는 origin-only 리퍼러를 사용해 명시적 `page_view`를 정확히 한 번 보낸다.
6. 그 밖의 행동 이벤트는 모두 버린다.

Google 스크립트가 로드되지 않거나 전송에 실패해도 페이지 탐색과 CTA 작동에는 영향을 주지 않는다.

### 명시적 동의 이후

사용자가 허용하면 `analytics_storage`, `ad_storage`, `ad_user_data`, `ad_personalization`을 `granted`로 갱신한다. 이후부터 기존 Google Analytics 사용자 행동 이벤트와 Meta Pixel을 활성화한다. 동의 이전에 발생한 클릭·스크롤·신청 퍼널 이벤트를 큐에 보관하거나 소급 전송하지 않는다.

### 거부 또는 동의 철회

네 가지 신호를 모두 `denied`로 유지하거나 되돌리고, Google 사용자 행동 이벤트와 Meta Pixel을 즉시 차단한다. 스크립트에서 접근할 수 있는 GA·Meta 1차 쿠키는 가능한 범위에서 삭제한다. 마케팅 페이지에서 이미 전송된 최소 페이지뷰는 취소할 수 없으며 추가 페이지뷰를 재전송하지 않는다.

## URL 및 UTM 최소화

비동의 페이지뷰에 허용되는 파라미터는 다음 여섯 개뿐이다.

- `utm_source`
- `utm_medium`
- `utm_campaign`
- `utm_id`
- `utm_content`
- `utm_term`

정제 규칙은 다음과 같다.

- `page_location`은 현재 origin과 pathname에 허용된 UTM만 다시 조합한다.
- 각 값은 앞뒤 공백을 제거하고 최대 100자로 제한한다.
- 이메일 주소 또는 전화번호 형태로 보이는 값은 해당 키 전체를 제외한다.
- 빈 값, 중복 값, 그 밖의 모든 쿼리 파라미터와 URL fragment는 제외한다.
- URL 파싱이나 정제 중 오류가 나면 origin과 pathname만 사용한다.
- `page_referrer`는 리퍼러가 유효한 HTTP(S) URL일 때 origin만 사용하고, 아니면 빈 문자열을 사용한다.
- `url_passthrough`는 사용하지 않는다.

정제 함수는 순수 함수로 분리해 테스트하며 결과를 어떤 저장소에도 기록하지 않는다.

## 개인정보 보호 신호

브라우저가 Global Privacy Control(GPC) 또는 Do Not Track(DNT)을 명시하면 동의 전의 쿠키 없는 페이지뷰도 보내지 않는다. 사용자가 별도로 분석을 허용하는 경우에는 명시적 선택을 우선하되, 동의 UI에서 현재 상태를 정확히 보여준다.

## 신청 데이터와 분석 데이터의 분리

현재 `/apply/` 요청에는 `document.referrer`가 포함되고 API는 이를 Google Sheets의 기존 `referrer` 열에 저장한다. 같은 출처에서 이동할 때 랜딩 URL의 UTM이 리퍼러에 포함될 가능성이 있으므로 이를 제거한다.

- 브라우저의 신청 payload에서 `referrer`를 삭제한다.
- API는 클라이언트가 임의로 보낸 `referrer` 값을 읽거나 저장하지 않는다.
- 고정된 17개 Google Sheets 열 순서는 바꾸지 않고, 기존 `referrer` 위치에는 빈 문자열을 기록한다.
- 신청 payload와 Sheets 행에 자동 수집 UTM을 추가하지 않는다.
- 신청 폼의 `source`는 사용자가 직접 선택·입력하고 신청 개인정보 처리에 동의한 답변이므로 유지한다.
- 분석 동의 후 전송되는 `application_submitted`에는 현재처럼 범주형 `source`만 허용하고 자유 입력인 `sourceOther`는 보내지 않는다.

테스트는 브라우저 payload에 `document.referrer`가 없고 API가 외부 `referrer` 입력을 무시하며 Sheets의 해당 열을 빈 값으로 유지하는지 보장해야 한다.

## 동의 UI와 공개 고지

모든 공개 페이지의 영문·국문 동의 배너를 다음 사실에 맞게 갱신한다.

- 랜딩·소개·이벤트 같은 마케팅 페이지에서는 선택적 쿠키를 허용하지 않아도 제한된 쿠키 없는 방문·캠페인 측정이 이루어진다.
- 비동의 측정에는 정제된 페이지 경로, 허용된 UTM, 리퍼러 origin만 사용한다.
- 클릭, 스크롤, 신청 퍼널 이벤트와 Meta Pixel은 명시적 허용 뒤에만 활성화한다.
- 신청 폼에 입력한 내용은 비동의 분석에 포함되지 않으며 UTM과 자동 연결하지 않는다.
- 사용자는 언제든 설정을 다시 열어 선택을 변경할 수 있다.

별도 `/privacy/` 페이지를 추가하고 모든 페이지 footer에서 연결한다. 이 페이지에는 최소 수집 필드와 목적, Google·Meta 제공자, 동의 전후 차이, 신청 개인정보 처리와의 분리, 설정 변경 방법을 영문과 국문으로 설명한다. `/privacy/index.html`은 `.vercelignore` 공개 allowlist에 포함한다.

문구는 “완전 익명”이나 “법적으로 안전”처럼 보장할 수 없는 표현을 사용하지 않는다.

## 코드 구조

공통 분석 로직은 계속 `assets/analytics.js`에 둔다. 페이지가 개인정보 입력 페이지인지 판별할 수 있도록 명시적인 페이지 정책 또는 DOM 표식을 추가하고, 분석 모듈이 이를 기준으로 초기화 방식을 선택한다.

예상 변경 파일:

- `assets/analytics.js`: 페이지 정책, 동의 기본값, 정제 함수, 명시적 페이지뷰, GPC/DNT 처리, 동의 전환
- `index.html`, `about/index.html`, `events/*/index.html`, `apply/index.html`: 동의 문구와 개인정보 페이지 표식, footer 링크
- `apply/index.html`: 신청 payload의 `referrer` 제거
- `api/apply.js`: 외부 referrer 무시 및 빈 열 유지
- `privacy/index.html`: 공개 분석·개인정보 안내
- `.vercelignore`: privacy 페이지 배포 허용
- `tests/*.test.js`: 분석 정책, 정제, 신청 데이터 분리, 문구와 배포 범위 회귀 테스트

## 오류 처리

- 잘못된 URL이나 UTM은 예외를 외부로 던지지 않고 path-only 페이지뷰로 축소한다.
- Google 또는 Meta 스크립트 로드 실패는 조용히 무시하고 사이트 기능을 막지 않는다.
- 동의 저장값이 없거나 손상되면 `denied`로 처리한다.
- 같은 페이지에서 초기화가 중복 호출되어도 비동의 페이지뷰는 한 번만 전송한다.
- 개인정보 페이지 판별에 실패하면 더 보수적인 `/apply/` 정책을 선택할 수 있도록 명시적 표식과 경로 검사를 함께 사용한다.

## 테스트 전략

`node --test tests/*.test.js`로 다음을 검증한다.

### 분석 초기화

- 마케팅 페이지의 미선택·거부 상태에서 모든 동의 신호가 `denied`다.
- 마케팅 페이지에서 정제된 쿠키 없는 페이지뷰가 정확히 한 번 발생한다.
- `/apply/`에서는 사전 동의 사용자가 아닌 한 Google 태그가 로드되지 않는다.
- 비운영 호스트와 GPC/DNT 환경에서는 비동의 전송이 없다.

### 최소수집

- 여섯 UTM만 유지되고 기타 쿼리·fragment는 제거된다.
- UTM 길이 제한, 이메일·전화번호 제외, 잘못된 URL fallback이 적용된다.
- 리퍼러는 origin만 남는다.
- `send_page_view: false`, 광고 데이터 편집, Signals·개인화 비활성 설정이 유지된다.

### 동의 전환

- 허용 전에는 Meta와 사용자 행동 이벤트가 차단된다.
- 허용 후 기존 이벤트와 Meta가 활성화된다.
- 거부·철회 후 다시 차단되고 접근 가능한 관련 쿠키 삭제를 시도한다.
- 동의 전 이벤트가 허용 뒤 소급 전송되지 않는다.

### 신청 분리

- `/apply/` payload가 `document.referrer`와 UTM을 포함하지 않는다.
- API가 전달된 `referrer`를 무시하고 Sheets의 기존 열에는 빈 값을 넣는다.
- 자유 입력 `sourceOther`가 분석 이벤트로 전송되지 않는다.

### 공개 표면

- 공통 영문·국문 동의 문구가 모든 페이지에서 동기화된다.
- footer의 `/privacy/` 링크와 `.vercelignore` allowlist가 존재한다.
- privacy 페이지가 최소수집과 신청 데이터 분리를 정확히 설명한다.

## 배포 및 검증

1. 구현 후 전체 Node 테스트를 통과시킨다.
2. 로컬 preview에서 마케팅 페이지와 `/apply/`의 동의 배너, 설정 변경, 신청 흐름을 확인한다.
3. PR preview에서 탐색과 신청이 분석 스크립트 실패와 무관하게 작동하는지 확인한다.
4. 분석 전송은 운영 도메인에서만 활성화되므로, 병합 후 Google Tag Assistant 또는 브라우저 네트워크 패널로 다음을 제한적으로 확인한다.
   - 비동의 마케팅 페이지: 정제된 페이지뷰 1회, 쿠키 없음, 행동 이벤트·Meta 없음
   - 비동의 `/apply/`: Google·Meta 요청 없음
   - 동의 후: 기존 GA 이벤트와 Meta 활성화
   - 신청 요청·Sheets 행: referrer와 UTM 없음
5. GA4 실시간/DebugView에서 허용된 UTM 차원이 예상대로 집계되는지 확인하고 민감한 쿼리가 유입되지 않는지 점검한다.

## 위험과 완화

- **비동의 ping에도 기술 정보가 전달될 수 있음:** 전송 페이지를 마케팅 페이지로 제한하고 URL·리퍼러를 사전 정제하며 GPC/DNT를 존중한다.
- **UTM에 개인정보를 넣는 잘못된 광고 링크:** 이메일·전화번호 패턴을 제외하고 길이를 제한한다. 캠페인 운영 규칙에도 UTM에 개인정보를 넣지 않도록 명시한다.
- **신청 데이터와 캠페인 데이터의 결합:** `/apply/`의 동의 전 태그와 referrer 저장을 제거하고 서버·Sheets에 UTM을 기록하지 않는다.
- **중복 페이지뷰:** 자동 페이지뷰를 끄고 모듈 수준 1회 가드를 테스트한다.
- **고지와 실제 동작의 불일치:** 공통 문구 회귀 테스트와 privacy 페이지 테스트를 추가한다.
- **규정 또는 Google 동작 변경:** 공개 문서와 실제 네트워크 전송을 배포 전에 다시 확인하고, 필요하면 고급 모드를 끌 수 있도록 로직을 한 모듈에 모은다.

## 승인 기준

- 비동의 상태에서 운영 마케팅 페이지의 정제된 UTM 방문량만 집계된다.
- 비동의 상태에서 사용자 행동, Meta, 신청 페이지 활동은 전송되지 않는다.
- UTM과 브라우저 리퍼러가 신청 payload, Google Sheets, Discord에 저장되지 않는다.
- 동의 후 기존 분석 퍼널은 계속 작동한다.
- 영문·국문 고지와 실제 동작이 일치하고 전체 테스트가 통과한다.
